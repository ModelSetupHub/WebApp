# Model Setup Hub — رابط گرافیکی وب

یک رابط وب محلی برای جعبه‌ابزار [ModelSetupHub Core](https://github.com/ModelSetupHub/Core). هر دکمه در این داشبورد
مستقیماً یک تابع core را صدا می‌زند، پس کنترل کامل آنچه روی دستگاه شما اجرا می‌شود دست خودتان می‌ماند — بررسی سخت‌افزار،
مدیریت سرویس Ollama، کار با مدل‌های محلی، و بنچمارک کردن پارامترهای تولید در برابر یکدیگر.

English: [README.md](README.md)

![تب System](docs/screenshots/system.png)

## این نسخه برای چه کسی است

Model Setup Hub همان جعبه‌ابزار را از دو مسیر ارائه می‌دهد و این دو برای دو گروه متفاوت‌اند:

- **این ریپو (رابط گرافیکی)** — برای کاربرانی که می‌دانند می‌خواهند چه کار کنند. مدل، پارامترها و ترتیب کارها را خودتان
  انتخاب می‌کنید. هیچ تصمیمی جای شما گرفته نمی‌شود؛ این کار را سریع‌تر و دقیق‌تر می‌کند، اما فرض می‌گیرد می‌دانید
  context window یا تعداد لایه‌های GPU چه معنایی دارد.
- **سرور MCP** — برای کاربرانی که ترجیح می‌دهند هدف را به زبان معمولی توصیف کنند و یک AI agent همان ابزارها را برایشان
  اجرا کند. اگر مطمئن نیستید کدام مدل با سخت‌افزارتان می‌خواند یا کدام پارامتر را باید عوض کنید، از آن استفاده کنید.

هر دو با همان پکیج `core` کار می‌کنند، پس روی یک دستگاه قابل جایگزینی با یکدیگرند.

## داشبورد چه کاری انجام می‌دهد

رابط یک صفحه‌ی واحد با چهار تب در ستون چپ است.

### System

یک اسکن کامل سخت‌افزاری: پردازنده، ماژول‌های RAM، کارت‌های گرافیک همراه VRAM، دیسک‌ها با نوار میزان مصرف، و جزئیات سیستم
عامل. اسکن به PowerShell و `nvidia-smi` متوسل می‌شود و چند ثانیه طول می‌کشد، پس نتیجه در حافظه cache می‌شود — با دکمه‌ی
**Refresh** یک اسکن تازه بگیرید. این تب را اول ببینید: عدد VRAM همین‌جا تعیین می‌کند چه مدل‌هایی واقعاً قابل بارگذاری‌اند.

### Ollama

![تب Ollama](docs/screenshots/ollama.png)

وضعیت نصب و پروسه‌ی سرور محلی. سرور را روشن و خاموش کنید، نسخه‌اش را ببینید، و نصب‌کننده‌ای که از قبل روی دستگاه دانلود
شده را اجرا کنید.

یک رفتار که دانستنش مهم است: در ویندوز، اپلیکیشن دسکتاپ Ollama سرور را نظارت می‌کند و بلافاصله بعد از kill دوباره بالا
می‌آورد. در این حالت صفحه صریحاً همین را می‌گوید و ادعای توقفی که نگرفته نمی‌کند — اگر باید خاموش بماند، Ollama را از
system tray ببندید.

### Models

![تب Models](docs/screenshots/models.png)

هر چه core برای مدل‌ها ارائه می‌دهد: فهرست نصب‌شده‌ها و فهرست بارگذاری‌شده‌ها در حافظه، به‌همراه **Info**، **Load**،
**Stop** و **Remove** در هر سطر. پایین جدول‌ها چهار فرم هست — اجرای یک پرامپت، بارگذاری مدل با بازه‌ی `keep_alive`، ثبت
یک فایل GGUF محلی، و ساختن یک کپی کانفیگ‌شده از مدلی موجود.

فرم آخر را باید از تب Benchmark جدا دید: `configure_model` یک Modelfile می‌نویسد و **یک مدل جدید روی دیسک** می‌سازد. مدل
مبدأ هرگز تغییر نمی‌کند. حذف مدل از این رابط قابل بازگشت نیست، پس اول تأیید می‌گیرد.

هر عمل خودش را همزمان در سه جا گزارش می‌دهد — پنل Output در پایین تب متن کامل نتیجه را نگه می‌دارد، یک toast در گوشه
پیشرفت را دنبال می‌کند، و دکمه‌ای که عمل را شروع کرده اسپینر نشان می‌دهد.

### Benchmark

اینجا بیشترین تفاوت را با بقیه‌ی تب‌ها دارد. همان پرامپت‌ها را با چند مجموعه پارامتر مختلف روی یک مدل اجرا می‌کند و
هزینه‌ی هر کدام را مقایسه می‌کند، تا بتوانید تصمیم بگیرید کدام کانفیگ را نگه دارید.

**مرحله ۱ — Target.** مدل را انتخاب کنید، بعد پرامپت‌ها را بنویسید. پرامپت‌ها با **یک خط خالی** از هم جدا می‌شوند؛ این
باعث می‌شود یک پرامپت چندخطی سالم بماند و همزمان بتوان چند پرامپت داد. هر کانفیگ همه‌ی پرامپت‌ها را اجرا می‌کند، و مدل
قبل از هر پرامپت پیش‌بارگذاری می‌شود تا زمان load هرگز داخل زمان‌سنجی‌ها نیفتد.

**مرحله ۲ — Configurations.** به دو روش می‌توانید اضافه کنید.

*به‌صورت دستی* — فرمی با ۲۳ گزینه‌ی تولید Ollama، دسته‌بندی‌شده در پنج گروه Sampling، Context and output، Repetition،
Mirostat و Runtime. فیلد خالی به معنی «به پیش‌فرض مدل دست نزن» است و هرگز ارسال نمی‌شود؛ به همین دلیل گزینه‌های بولی یک
select سه‌گزینه‌ای هستند نه چک‌باکس: `not set` و `false` برای Ollama دو چیز متفاوت‌اند. فیلدی که مقدار دارد رنگی می‌شود و
هر گروه بسته هم تعداد گزینه‌های تنظیم‌شده‌اش را اعلام می‌کند.

![فرم دستی کانفیگ](docs/screenshots/benchmark-builder.png)

*از فایل* — یک فایل `.json` را روی drop zone بکشید، با file browser انتخابش کنید، یا متنش را paste کنید. فایل اول در
سرور اعتبارسنجی می‌شود و پیش‌نمایشی از آنچه فهمیده شده می‌گیرید، بعد بین **Add to list** و **Replace existing** انتخاب
می‌کنید. اعمال کردن عمداً یک مرحله‌ی جداست: فایل ممکن است مدل و پرامپت هم داشته باشد و این‌ها نباید بی‌صدا چیزی را که
خودتان نوشته‌اید بازنویسی کنند.

![بارگذاری فایل کانفیگ](docs/screenshots/benchmark-import.png)

چهار شکل سند پذیرفته می‌شود:

```jsonc
// یک ستاپ کامل
{ "model": "...", "prompts": ["..."], "configurations": [ ... ] }

// فقط یک لیست از کانفیگ‌ها
[ { "name": "baseline", "options": { "temperature": 0.7 } } ]

// یک کانفیگ تنها
{ "name": "baseline", "options": { "temperature": 0.7 } }

// یک آبجکت خالی از گزینه‌ها — خودش شماره‌گذاری می‌شود
{ "temperature": 0.7, "num_ctx": 4096 }
```

کلیدهایی که برنامه نمی‌شناسد رد نمی‌شوند و دست‌نخورده پاس داده می‌شوند، پس فایلی که برای نسخه‌ی جدیدتر Ollama نوشته شده
هم اینجا کار می‌کند. دکمه‌ی **Export setup** مدل، پرامپت‌ها و کانفیگ‌های فعلی را به‌صورت فایلی می‌نویسد که بعداً قابل
بارگذاری مجدد است.

هر کارت کانفیگ سه عمل دارد: **Edit**، **Duplicate** و **Remove**. Duplicate راه ساختن یک نسخه‌ی متغیر است: همه‌چیز را
نگه دار، یک گزینه را عوض کن. همین هم توصیه‌ی رسیدن به اعداد معنادار است — اگر دو کانفیگ در چند جا فرق داشته باشند،
نمی‌توانید اختلاف را به هیچ‌کدام نسبت دهید. `seed` را روی مقداری ثابت بگذارید تا اجراها تکرارپذیر شوند، و هر بار فقط یک
پارامتر را تغییر دهید.

**مرحله ۳ — Run.** نوار وضعیت می‌گوید چرا هنوز آماده نیست (`no prompts were written`، `no configurations were added`) و
در حین اجرا کل ستاپ را قفل می‌کند، چون اجرا نسخه‌ی خودش از آن را در دست دارد. هر بار فقط یک مقایسه اجرا می‌شود: دو
مقایسه‌ی همزمان برای یک GPU رقابت می‌کنند و همه‌ی زمان‌سنجی‌های هر دو را بی‌معنا می‌کنند.

مقایسه‌ها دقایق طول می‌کشند، پس در یک ترد پس‌زمینه روی سرور اجرا می‌شوند و صفحه نتیجه را poll می‌کند. رفرش مرورگر اجرای
در جریان را از دست نمی‌دهد — job روی سرور زندگی می‌کند و صفحه دوباره آن را برمی‌دارد.

**نتایج.** اول حکم می‌آید: کدام کانفیگ سریع‌تر تولید کرد و با چه اختلافی نسبت به نفر دوم. بعد سه بلوک میله‌ای — سرعت
تولید، سرعت پرامپت، زمان پاسخ — که هر کدام نسبت به بهترین مقدار بلوک خودش مقیاس می‌شود، و برای زمان پاسخ مقیاس معکوس
می‌شود تا بهترین مقدار در هر سه بلوک میله‌ی پر باشد. سپس جدول خلاصه با سلول برنده‌ی هر ستون به‌صورت برجسته، و در آخر یک
بخش تاشو برای هر کانفیگ با زمان‌سنجی هر پرامپت و — اگر **Keep generated text** تیک خورده باشد — خود متن تولیدشده.

![نتایج بنچمارک](docs/screenshots/benchmark-results.png)

پرامپت ناموفق پنهان نمی‌شود بلکه گزارش می‌شود: سطر می‌گوید چند مورد شکست خورده و پنل جزئیات متن خطا را مستقیماً از Ollama
می‌آورد، که معمولاً همان چیزی است که لازم دارید — کمبود حافظه در هنگام راه‌اندازی، خطای مقدارگذاری CUDA و مانند آن.

## پیش‌نیازها

- پایتون ۳.۱۰ یا بالاتر
- ویندوز — اسکنر سخت‌افزار از PowerShell و WMI استفاده می‌کند
- نصب بودن [Ollama](https://ollama.com/) برای همه‌چیز به‌جز تب System
- Git، برای دریافت ساب‌ماژول core

## راه‌اندازی

`core` یک ساب‌ماژول git است، نه یک کپی از کد، و پیش از آنکه برنامه بتواند آن را import کند باید به‌صورت پکیج نصب شود. هر
دو مرحله لازم‌اند.

```bash
# ۱. کلون همراه با ساب‌ماژول
git clone --recurse-submodules https://github.com/ModelSetupHub/gui.git
cd gui

# قبلاً بدون --recurse-submodules کلون کرده‌اید؟ الان دریافتش کنید:
git submodule update --init --recursive
```

```bash
# ۲. ساختن محیط مجازی توصیه می‌شود
python -m venv .venv
source .venv/Scripts/activate     # Git Bash در ویندوز
# .venv\Scripts\activate          # PowerShell / cmd
```

```bash
# ۳. نصب ساب‌ماژول core به‌صورت پکیج editable، سپس وابستگی‌های وب
pip install -e ./core
pip install -r requirements.txt
```

```bash
# ۴. اجرا
python app.py
```

آدرس <http://127.0.0.1:5000/> را باز کنید.

مرحله‌ی `pip install -e ./core` همان مرحله‌ای است که راحت از قلم می‌افتد. بدون آن هر درخواست با
`ModuleNotFoundError: No module named 'MSHCore'` شکست می‌خورد، چون برنامه پکیج ساب‌ماژول (`MSHCore`) را با نام import می‌کند نه با مسیر فایل.

## نکاتی درباره‌ی اجرا

سرور توسعه با `debug=True` روی پورت ۵۰۰۰ اجرا می‌شود و فقط به localhost گوش می‌دهد. **هیچ احراز هویتی ندارد** و
اندپوینت‌هایش Ollama را استارت می‌کنند، مدل بارگذاری و حذف می‌کنند، و نصب‌کننده روی دستگاه اجرا می‌کنند. آن را در وضعیت
فعلی روی یک اینترفیس شبکه یا پشت یک reverse proxy عمومی قرار ندهید.

دو بخش از وضعیت برنامه در پروسه‌ی سرور نگه داشته می‌شود نه روی دیسک: اسکن cache‌شده‌ی سخت‌افزار و job بنچمارک جاری.
ری‌استارت سرور هر دو را پاک می‌کند. کانفیگ‌هایی که در تب Benchmark می‌سازید در صفحه‌ی مرورگر زندگی می‌کنند — اگر
می‌خواهید نگه‌شان دارید از **Export setup** استفاده کنید.

## ساختار پروژه

```text
gui/
├── app.py                       # نقطه ورود؛ برنامه را می‌سازد و اجرا می‌کند
├── requirements.txt
├── core/                        # ساب‌ماژول git ← ModelSetupHub/Core (پکیج: MSHCore)
├── webapp/
│   ├── __init__.py              # create_app و ثبت blueprint‌ها
│   ├── responses.py             # پوشش JSON مشترک و ترجمه استثناهای core
│   ├── routes/                  # یک blueprint برای هر حوزه
│   │   ├── pages.py             # ارائه داشبورد
│   │   ├── system.py            # /api/system
│   │   ├── runtime.py           # /api/ollama/{status,start,stop,install}
│   │   ├── models.py            # /api/ollama/models/*
│   │   └── benchmark.py         # /api/benchmark/*
│   ├── services/                # وضعیتی که از یک درخواست بیشتر عمر می‌کند
│   │   ├── system_scan.py       # پروفایل سخت‌افزار cache‌شده
│   │   └── benchmark.py         # job مقایسه در پس‌زمینه
│   └── parsing/                 # تبدیل متن خارجی به ساختار قابل نمایش
│       ├── ollama_text.py       # جدول‌های CLI و خروجی `show`
│       ├── benchmark_options.py # اسکیمای گزینه‌ها که فرم از آن ساخته می‌شود
│       └── benchmark_config.py  # اعتبارسنجی کانفیگ و خواندن فایل
├── templates/
│   ├── base.html                # پوسته: head، سایدبار، میزبان toast
│   ├── dashboard.html
│   ├── partials/sidebar.html
│   └── sections/                # یک فایل برای هر تب
├── static/
│   ├── css/                     # توکن‌ها، چیدمان، کامپوننت‌ها
│   └── js/
│       ├── main.js              # هر پنل را bind می‌کند و داده‌شان را می‌گیرد
│       ├── lib/                 # api، actions، state، toast، console، format
│       └── panels/              # یک کنترلر برای هر تب
└── docs/screenshots/
```

هر اندپوینت API با یک پوشش یکسان پاسخ می‌دهد، تا مرورگر برای موفقیت و شکست یک مسیر کد داشته باشد:

```json
{ "ok": true, "error": null, "data": "..." }
```

core برای ورودی نامعتبر `ValueError`/`TypeError`/`FileNotFoundError` و در صورت خطای خود Ollama `RuntimeError` پرتاب
می‌کند؛ گروه اول به HTTP 400 و بقیه به 500 نقشه می‌شوند. جایی که توضیح خود Ollama فقط روی cause استثنا باقی می‌ماند،
خوانده و به پیام اضافه می‌شود.
