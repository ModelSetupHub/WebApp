# ModelSetupHub — WebApp

**داشبورد وب محلی برای راه‌اندازی، اجرا و اندازه‌گیری مدل‌های AI روی دستگاه خودتان.**

[English](README.md) · فارسی

WebApp رابط گرافیکی ModelSetupHub است. روی کامپیوتر خودتان و در مرورگر خودتان اجرا می‌شود و کل جعبه‌ابزار را در یک صفحه
می‌گذارد: بررسی سخت‌افزار، کنترل سرویس Ollama، مدیریت مدل‌های محلی، و مقایسه‌ی تنظیمات تولید با یکدیگر تا ببینید کدام
واقعاً سریع‌تر است. هیچ تصمیمی جای شما گرفته نمی‌شود — مدل، پارامترها و ترتیب کارها را خودتان انتخاب می‌کنید.

![تب System](docs/screenshots/system.png)

## جای این ریپو در پروژه

ModelSetupHub سه ریپو روی یک موتور مشترک است.

| ریپو | چیست | کِی به آن سر بزنید |
| --- | --- | --- |
| [Core](https://github.com/ModelSetupHub/Core) | کتابخانه‌ی پایتونی که کار را انجام می‌دهد | وقتی خودتان اسکریپت یا automation می‌نویسید |
| **WebApp** (همین) | داشبورد وب محلی روی همان توابع | وقتی رابط گرافیکی و کنترل کامل دستی می‌خواهید |
| [MCPServer](https://github.com/ModelSetupHub/MCPServer) | سرور MCP که همان ابزارها را به یک AI agent می‌دهد | وقتی ترجیح می‌دهید هدف را به زبان معمولی توصیف کنید |

این داشبورد فرض می‌گیرد که می‌دانید می‌خواهید چه کار کنید — برای همان حالت سریع‌تر و دقیق‌تر است، اما انتظار دارد بدانید
context window یا تعداد لایه‌های GPU چه معنایی دارد. اگر مطمئن نیستید کدام مدل با سخت‌افزارتان می‌خواند یا کدام پارامتر
را باید عوض کنید، سرور MCP مسیر دوستانه‌تری است. هر دو با کتابخانه‌ی یکسانی کار می‌کنند، پس روی یک دستگاه قابل جایگزینی
با یکدیگرند.

## داشبورد چه کاری انجام می‌دهد

یک صفحه، چهار تب در ستون کنار، به همان ترتیبی که معمولاً به آن‌ها نیاز پیدا می‌کنید. رابط به دو زبان انگلیسی و فارسی
موجود است، با چیدمان کامل راست‌به‌چپ.

### System

یک اسکن کامل سخت‌افزاری: پردازنده، ماژول‌های حافظه، کارت‌های گرافیک همراه VRAM، دیسک‌ها با نوار میزان مصرف، و جزئیات
سیستم‌عامل. از اینجا شروع کنید — عدد VRAM همان چیزی است که تعیین می‌کند واقعاً چه مدل‌هایی قابل بارگذاری‌اند. اسکن چند
ثانیه طول می‌کشد، پس نتیجه نگه داشته و دوباره استفاده می‌شود؛ هر وقت نتیجه‌ی تازه خواستید **Rescan** را بزنید.

### Ollama

![تب Ollama](docs/screenshots/ollama.png)

وضعیت نصب و پروسه‌ی سرور محلی، همه در یک جا: روشن کردن، خاموش کردن، خواندن نسخه، و نصب Ollama از نصب‌کننده‌ای که روی
دستگاه هست.

یک رفتار که دانستنش مهم است: در ویندوز، اپلیکیشن دسکتاپ Ollama سرور را نظارت می‌کند و بلافاصله بعد از توقف دوباره بالا
می‌آورد. در این حالت صفحه صریحاً همین را می‌گوید و ادعای توقفی که نگرفته نمی‌کند — اگر باید خاموش بماند، Ollama را از
system tray ببندید.

### Models

![تب Models](docs/screenshots/models.png)

فهرست مدل‌های نصب‌شده و فهرست مدل‌های حاضر در حافظه، که هر سطر امکان مشاهده‌ی اطلاعات، بارگذاری، توقف و حذف را می‌دهد.
پایین‌شان فرم‌هایی هست برای اجرای یک پرامپت، بارگذاری مدل با بازه‌ی keep-alive، ثبت یک فایل GGUF محلی، و ساختن یک کپی
کانفیگ‌شده از مدلی موجود. مورد آخر **یک مدل جدید روی دیسک** می‌نویسد و نسخه‌ی اصلی را دست‌نخورده می‌گذارد. حذف مدل قابل
بازگشت نیست، پس اول تأیید می‌گیرد.

هر عمل خودش را همزمان در سه جا گزارش می‌دهد: پنل خروجی متن کامل نتیجه را نگه می‌دارد، یک toast در گوشه پیشرفت را دنبال
می‌کند، و دکمه‌ای که زده‌اید اسپینر نشان می‌دهد.

### Benchmark

این قابلیت شاخص پروژه است. همان پرامپت‌ها را با چند مجموعه پارامتر مختلف روی یک مدل اجرا می‌کند و هزینه‌ی هر کدام را
مقایسه می‌کند، تا بتوانید تصمیم بگیرید کدام کانفیگ را نگه دارید.

**هدف را انتخاب کنید.** مدل را انتخاب کنید، بعد پرامپت‌ها را بنویسید — با یک خط خالی از هم جدا می‌شوند، که باعث می‌شود
یک پرامپت چندخطی سالم بماند و همزمان بتوان چند پرامپت داد. هر کانفیگ همه‌ی پرامپت‌ها را اجرا می‌کند و مدل قبل از هر
پرامپت پیش‌بارگذاری می‌شود تا زمان بارگذاری هرگز داخل زمان‌سنجی‌ها نیفتد.

**کانفیگ‌ها را بسازید.** یا دستی، با فرمی که ۲۳ گزینه‌ی تولید را در گروه‌های Sampling، Context and output،
Repetition، Mirostat و Runtime پوشش می‌دهد — فیلد خالی به معنی «به پیش‌فرض مدل دست نزن» است و هرگز ارسال نمی‌شود. یا از
یک فایل: یک فایل `.json` را روی صفحه رها کنید، از میان فایل‌ها انتخابش کنید، یا متنش را بچسبانید. پیش از اعمال شدن روی
سرور بررسی و پیش‌نمایش می‌شود، چون یک فایل ممکن است مدل و پرامپت‌های خودش را هم داشته باشد و آن‌ها نباید بی‌صدا چیزی را
که نوشته‌اید بازنویسی کنند. دکمه‌ی **Export setup** مدل، پرامپت‌ها و کانفیگ‌های فعلی را به‌صورت فایلی می‌نویسد که بعداً
قابل بارگذاری مجدد است.

![فرم دستی کانفیگ](docs/screenshots/benchmark-builder.png)

![بارگذاری فایل کانفیگ](docs/screenshots/benchmark-import.png)

هر کانفیگ را می‌توان ویرایش، تکثیر یا حذف کرد. تکثیر کردن راه ساختن یک نسخه‌ی متغیر است: همه‌چیز را نگه دار، یک گزینه را
عوض کن. همین هم توصیه‌ی رسیدن به اعداد معنادار است — seed را ثابت کنید تا اجراها تکرارپذیر شوند، و هر بار فقط یک پارامتر
را تغییر دهید. اگر دو کانفیگ در چند جا فرق داشته باشند، نمی‌توانید اختلاف را به هیچ‌کدام نسبت دهید.

**اجرا کنید و نتیجه را بخوانید.** یک مقایسه چند دقیقه طول می‌کشد، پس روی سرور اجرا می‌شود و صفحه آن را دنبال می‌کند؛
رفرش مرورگر اجرای در جریان را از دست نمی‌دهد. هر بار فقط یک مقایسه اجرا می‌شود، چون دو مقایسه‌ی همزمان برای یک GPU
رقابت می‌کنند و همه‌ی زمان‌سنجی‌های هر دو را بی‌معنا می‌سازند.

نتیجه با حکم شروع می‌شود: کدام کانفیگ سریع‌تر تولید کرد و با چه اختلافی نسبت به نفر دوم. بعد سه بلوک میله‌ای — سرعت
تولید، سرعت پرامپت و زمان پاسخ — که هر کدام نسبت به بهترین مقدار بلوک خودش مقیاس می‌شود، سپس جدول خلاصه با مقدار برنده‌ی
هر ستون به‌صورت برجسته، و در آخر یک بخش تاشو برای هر کانفیگ با زمان‌سنجی هر پرامپت و — اگر خواسته باشید نگه داشته شود —
خود متن تولیدشده.

![نتایج بنچمارک](docs/screenshots/benchmark-results.png)

پرامپت ناموفق پنهان نمی‌شود بلکه گزارش می‌شود: سطر می‌گوید چند مورد شکست خورده و بخش جزئیات متن خطا را مستقیماً از
Ollama می‌آورد، که معمولاً همان چیزی است که لازم دارید — کمبود حافظه در هنگام راه‌اندازی، خطای مقدارگذاری CUDA و مانند
آن.

## پیش‌نیازها

- پایتون ۳.۱۰ یا جدیدتر
- ویندوز برای اسکن کامل سخت‌افزار، که بر PowerShell و WMI تکیه دارد
- Git، برای دریافت ساب‌ماژول `core`

وابستگی‌ها در `requirements.txt` پین شده‌اند. خودِ جعبه‌ابزار از ساب‌ماژول `core` می‌آید و وابستگی‌های خودش را همراه دارد.

## راه‌اندازی

`core` یک ساب‌ماژول git است، نه یک کپی از کد، و پیش از آنکه برنامه بتواند آن را import کند باید به‌صورت پکیج نصب شود.
هر دو مرحله لازم‌اند.

<div dir="ltr">

```bash
# 1. clone with the submodule
git clone --recurse-submodules https://github.com/ModelSetupHub/WebApp.git
cd WebApp

# already cloned without --recurse-submodules? fetch it now:
git submodule update --init --recursive
```

```bash
# 2. a virtual environment is recommended
python -m venv .venv
.venv\Scripts\activate            # PowerShell / cmd
# source .venv/Scripts/activate   # Git Bash on Windows
```

```bash
# 3. install the core submodule as a package, then the web dependencies
pip install -e ./core
pip install -r requirements.txt
```

```bash
# 4. run it
python app.py
```

</div>

بعد آدرس <http://127.0.0.1:5000/> را باز کنید.

مرحله‌ی `pip install -e ./core` همان مرحله‌ای است که راحت از قلم می‌افتد. بدون آن هر درخواست با
`ModuleNotFoundError: No module named 'MSHCore'` شکست می‌خورد، چون برنامه ساب‌ماژول را با نام پکیج import می‌کند نه با
مسیر فایل.

## خوب است بدانید

- **هیچ احراز هویتی وجود ندارد.** این یک سرور توسعه‌ی محلی است و اندپوینت‌هایش Ollama را استارت می‌کنند، مدل بارگذاری و
  حذف می‌کنند، و نصب‌کننده روی میزبان اجرا می‌کنند. آن را روی localhost نگه دارید — در وضعیت فعلی به یک اینترفیس شبکه
  متصلش نکنید و پشت یک reverse proxy عمومی نگذاریدش.
- **دو چیز در پروسه‌ی سرور نگه داشته می‌شود نه روی دیسک:** اسکن کش‌شده‌ی سخت‌افزار و بنچمارک در حال اجرا. ری‌استارت سرور
  هر دو را پاک می‌کند.
- **کانفیگ‌هایی که در تب Benchmark می‌سازید در صفحه‌ی مرورگر زندگی می‌کنند.** اگر می‌خواهید نگه‌شان دارید از
  **Export setup** استفاده کنید.
- **حذف مدل از این رابط قابل بازگشت نیست.**

[Core](https://github.com/ModelSetupHub/Core) مربوط‌اند، چون این داشبورد فقط آن را صدا می‌زند.
